# RustHost second-pass robustness audit — 2026-09-06

Scope: persistent-file crash consistency, site reload consistency, Tor/network transfer deadlines, and externally amplified runtime state. This follows `engineering-audit-2026-09-05.md`; the previous pass's uncommitted work was preserved. No commits or dependency upgrades were made. The existing Tokio dependency gains its development-only `test-util` feature for virtual-time regressions; the now-unused direct `pem-rfc7468` declaration was removed after consolidating PEM parsing. Its transitive dependency remains.

| Development certificate and key were truncated separately. Before renewal, durably publish the previous valid pair as `self-signed.previous.pem`. Import valid legacy `.crt`/`.key` pairs without changing identity or deleting originals. ## Persistence publication and crash analysis

The helper reserves `.rusthost-persist.lock` and `.rusthost-persist.tmp` in each participating directory. An OS lock serializes cooperating writers across processes; `&mut Directory` enforces exclusive staging access within a process. Lock contention fails promptly. Never remove the lock file while RustHost is using the directory. Reserved filenames and traversal components are rejected as publication targets.

1. **Before or during staging:** the live file is unchanged. A `create_new` staging file has mode 0600 from creation on Unix. A partial write or file-sync failure cannot replace the live file.
2. **After file sync, before publication:** the old live generation remains; the complete staging file is not authoritative.
3. **Publication:** same-directory rename switches replacement readers to the complete new inode. Default hard-link publication fails without overwriting an existing target. Existing open readers continue reading their old inode.
4. **After publication, before directory sync:** readers see a complete new file, but crash durability of the directory entry is not yet confirmed. Unix parent-directory `sync_all` is required before successful return. Relevant created directory ancestry is also synced.
5. **Cleanup:** normal completion/error removes staging. Abrupt process exit leaves at most one staging file per directory; the next writer removes it only after acquiring the stable OS lock. A staging file reappearing after power loss is similarly non-authoritative and recoverable.

For a development renewal or ACME cache update, the previous validated generation is published and synced before replacing current state. Failure between the two publications leaves a valid current pair and/or its backup; certificate and private key cannot come from different bundle generations. Account and certificate ACME files are independent objects: a certificate contains its own private key, not the ACME account key. If account persistence fails, issuance stops before the upstream loop starts using an unpersisted new account.

An error after successful rename, including directory-sync failure, **does not mean the old file remains visible**. It means durability is unconfirmed; old or new complete state may be visible on recovery. The implementation reports the error and does not attempt a destructive rollback. Defaults and reports have no previous-generation backup because defaults never replace existing files and reports are reproducible. Operator-written malformed settings still fail loading; RustHost does not guess another configuration.

These guarantees assume a local filesystem with the stated primitives and directories controlled by the operator. Rust's [`File::sync_all`](https://doc.rust-lang.org/stable/std/fs/struct.File.html) requests OS synchronization, not proof that every storage device honors it. Unit/process-crash tests do not simulate power loss. Windows has no portable directory flush through the standard library; rename durability, ACL inheritance, sharing violations, and replacement behavior need Windows testing. Filesystems without hard links fail default creation explicitly. Directory ancestor substitution by a hostile local writer remains outside the handle-based containment guarantees supplied here.

## Reload lifecycle and compatibility

`R` and SIGHUP are site reloads, **not settings reloads**. Existing docs already specify restart-only configuration. Ports, TLS acceptors, Tor sessions, redirect rules, logging, CSP, and other settings consequently retain the same configuration. Reload does not restart processes, tasks, sockets, or certificates.

Preparation happens on a blocking worker with no live routing mutation. Cancellation before publication drops the candidate result; the blocking scan itself may still finish, but it has no publisher. Normal UI/SIGHUP reload requests are serialized by the event loop. For direct concurrent calls, the Arc comparison allows only a candidate prepared from the still-current generation to replace it. No await exists between publication and statistic updates once the state lock is acquired. Requests that started earlier retain their snapshot; subsequent requests, including on keep-alive connections, select the new one. All three listener types use the same request entry point and watch source.

A site snapshot does not freeze directory contents. Operators must retain old physical deployment directories while requests use them, and publish deployments by switching a stable symlink or equivalent. In-place edits, ancestor renames, and removal of old files can still affect requests. Failed preparation retains cached custom pages and the previous root, but cannot undo external filesystem mutations.

Compatibility changes: development bundles use a new filename; missing/mismatched legacy pairs now require repair rather than automatic identity regeneration; configured but unreadable error pages and incomplete scans reject startup/reload rather than silently using defaults; manual TLS files are limited to 1 MiB each; library listener/reload watch payloads change from `Arc<Path>` to `Arc<SiteSnapshot>`; console channel types are bounded; connection lifetime and visitor-count limits are observable. Requests relying on special files are rejected. These changes are documented in README and the file tree.

## Network boundaries and remaining upstream concerns

| Boundary | Policy/evidence |
| --- | --- |
| Incoming HTTP/Tor-ingress first byte and complete headers | Five-second absolute header deadline; 16 KiB request buffer. Slow header progress does not extend it. Hyper applies the header limit/deadline to subsequent requests. |
| Incoming TLS, including ACME ALPN handling | Existing ten-second combined handshake deadline retained. |
| Tor bootstrap | Existing 120-second deadline, cancellable by shutdown; bounded exponential retry count/backoff retained. |
| Tor local TCP connect / stream accept | Five seconds / ten seconds. |
| HTTP response production and transfer | Inactivity covers reads and writes at the driver level: five seconds clearnet, 60 seconds Tor ingress. It also bounds a stalled first response/body when the driver is awaiting it. Individual write/flush/shutdown limits are 60 seconds, with shorter overall inactivity applying first. |
| Tor relay | 60-second connection-wide inactivity plus independent blocked I/O deadlines; 32 KiB copy buffer per direction. Successful download traffic does not require further uploads. Half-close follows [Tokio's bidirectional-copy contract](https://docs.rs/tokio/latest/tokio/io/fn.copy_bidirectional.html). |
| Extremely slow but progressing peers | HTTP driver and Tor relay each have a 24-hour total deadline. This intentionally allows long static downloads while preventing permanent slot retention. OS/TLS buffers can count accepted bytes as progress before the remote application consumes them; memory remains bounded and eventual backpressure/total deadlines apply. |
| HTTP redirects | Existing bounded header read plus ten-second response-write deadline. |
| Shutdown/reconnect | Existing grace periods remain; timed-out listener and Tor relay tasks are aborted and joined. Dropping a connection future drops its streams and admission guard. Tokio filesystem work and synchronous syscalls cannot be force-cancelled. |
| Doctor/network probes | Existing 200 ms/750 ms TCP connect deadlines retained. Windows ACL helpers now have five seconds, suppress captured output, and kill/reap. Browser/terminal launch paths spawn rather than await remote peers. |
| Outbound ACME — unresolved | The selected `rustls-acme`/`async-web-client` implementation has no exposed per-connect/TLS/first-byte/read/total deadline hook, and `https_helper.rs` reads response bodies into an unbounded `String`. A stalled or excessive authenticated ACME response can stall issuance/renewal or allocate excessive memory. The active certificate remains in the resolver; normal task cancellation still ends the async network operation. Wrapping `state.next()` in a timeout would also time legitimate months-long renewal sleeps, and dropping that temporary future does not cancel the order future retained inside `AcmeState`. A correct fix needs an upstream transport/body-limit hook or a maintained dependency patch, not that ineffective timeout. No speculative ACME state-machine rewrite was made. |
| Arti internals — upstream boundary | RustHost bounds bootstrap and accepted relay work. Arti manages circuit/directory scheduling and protocol resource quotas; its configured client stream connect/DNS defaults are ten seconds, but those alone do not prove bounds for every onion-service rendezvous/internal queue. Live Tor load and failure tests are still required. |

## Already sound or retained deliberately

- HTTP/HTTPS/Tor ingress share the application admission budget. Per-IP counters are removed on final guard drop; anonymous Tor clients do not create a new stable visitor identity per request. The prior admission-race and TLS-handshake corrections remain covered by tests.
- Normal file and compression bodies already stream under backpressure, with finite chunks and length bounds. Directory listing output retains its 512-entry cap. The separate console site-summary scan already has a total entry limit.
- Access logging retains its 4,096-record bounded queue with drop accounting. The display ring retains at most 1,000 messages. HTTP-derived strings are limited by request parsing; arbitrary dependency log messages can still be larger, including the unresolved ACME response-error path.
- Config vectors and diagnostic reports are operator-controlled, not indefinitely appended visitor histories. Request counters, status fields, retry counters, watch channels, and semaphore state use fixed-size storage or replacement semantics.
- Manual certificates are read and pair-validated, not rewritten by RustHost. Tor identity/databases are owned by Arti and were not manipulated by this audit.
- Append-only operational logs are intentionally best-effort diagnostics, not recoverable transactional state. A crash may lose buffered tail records or leave an incomplete final line; five-file rotation is not a multi-file transaction and is not fsynced. Readers do not use these logs as authoritative config/identity. Multiple independent processes writing the same logs remain unsupported for reliable rotation accounting.

## Unresolved durability and platform/integration testing

Arti's selected `tor-keymgr` persistence path delegates to `fs-mistrust` 0.14.2 `write_and_replace`: it writes a temporary file, drops it, then renames without a file or directory fsync. Therefore power-loss durability of onion key updates is **not established**, despite atomic replacement for normal process crashes. Other Tor persisted state/SQLite databases have upstream-specific recovery contracts; there is no application transaction spanning them. Strengthening this requires upstream work and crash/restart testing with an actual onion identity, not periodic application fsync calls after Arti has already reported success.

Other remaining tests: Windows/Linux execution and filesystem semantics; Windows ACL helper failures and non-Unix special-file behavior; APFS/ext4/NTFS power-cut fault injection at sync/rename boundaries; disk-full and directory-sync failures; live Tor stream acceptance, bootstrap/reconnection, half-close and sustained load; ACME staging issuance/renewal/recovery; shutdown during stalled filesystem operations. Linux-only non-UTF-8 path coverage from the prior pass remains unexecuted on this APFS host. A blocking filesystem or OS helper stuck in an uninterruptible kernel state can outlive cancellation; even kill/reap cannot promise a wall-clock bound in that case. Readiness does not currently distinguish stopped ACME issuance from a still-running listener with an existing certificate.

## Regression coverage

Added tests cover interrupted staging with a real subprocess exit and OS-lock release; failed writes preserving current state; concurrent readers seeing only complete generations; no-clobber defaults; stale-stage cleanup; cross-handle lock contention; private permissions, symlink rejection and reserved filenames; development legacy import, key mismatch and previous-bundle recovery; ACME filename compatibility and validated backup recovery; failed site preparation and depth limits; a symlink deployment switch on an existing keep-alive connection, refreshing index/favicon/custom 404 together and retaining the cached page after failed reload; a 16 MiB paced favicon download lasting longer than the read-idle window; FIFO rejection; concurrent IPv6 visitor churn at capacity; failed log rotation at its cap; bounded subprocess cleanup; and cancellation returning admission permits.

Virtual-time tests exercise idle-driver wakeups, blocked writes, a one-way Tor transfer over several idle windows, half-close, stalled receivers, idle relay termination, and continuous trickle traffic reaching the 24-hour deadline. Existing HTTP/TLS/path/logging/lifecycle regressions remain in the full suite. The ACME reinitialization test now aborts **and joins** the old task before asserting the cache can be opened again.
